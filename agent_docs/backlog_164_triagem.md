## Decisões documentadas (existe mas é intencional/aceitável) — 5

  - O código é semanticamente correto e a design é intencional (Q.116.D): permite distinguir "nenhuma facturação" de "dados indisponíveis" usando NULL. - **COGS endpoint N+1 risk: calculate_order_cogs bypasses service cache** (src/profit/api/cogs.py:81)
  - O problema descrito é real mas não é um N+1 clássico: o endpoint faz 2 queries fixas em vez de 1. Porém, a recomendação de usar joinedload é irrealizável — ProductionOrder.product_id é um Integer legado (sem FK), e Product é identificado por product_code (string), não por UUID, logo não existe relação ORM entre as entidades. Seria necessário um LEFT JOIN manual ou cache, ambos de baixíssima severidade comparado com o esforço. Nenhum commit posterior tentou corrigir, sugerindo que foi considerado aceitável ou prioridade negligenciável.
- **Default_configs seed_tenant_defaults enforces skip_existing=True, forbids overwrite** (src/core/services/default_configs.py:567)
  - Skip_existing=True é designação intencional — seeds são append-only por segurança. Se um default precisa actualizar, usa-se TenantConfigService.set() directamente (com auditoria). Comportamento validado por 3 testes (test_seed_writes_all_keys, test_seed_is_idempotent, test_seed_rejects_non_idempotent_mode) e documentado no docstring. NotImplementedError com mensagem clara quando alguém tenta skip_existing=False.
- **Tabs.test.tsx — mock empty onChange handlers in test cases** (frontend/src/components/dark/Tabs.test.tsx:20)
  - O padrão atual é intencional: testes de renderização/UI usam `onChange={() => {}}` (linhas 20, 27, 39, 59), enquanto testes de comportamento usam `vi.fn()` (linhas 44, 51). Não há bug funcional. A recomendação de adicionar comentário é cosmética; o código é claro pelo contexto (tests que precisam assertions já usam vi.fn).
- **Estado global mutável sem proteção em scheduler in-process: _last_run[tid] race entre leitura e escrita** (src/scheduling/jobs/auto_cpo_replan_job.py:46)
  - O estado `_last_run` não é uma race condition clássica em uvicorn multi-worker: cada worker tem sua própria cópia isolada em memória do dict, e `max_instances=1` garante apenas 1 execução simultânea do job. A "inconsistência" entre workers (cada um com seu `_last_run` local) é deliberada e **mitigada por Q.142.A via dedup determinístico `_job_id` no Arq**: ambos os workers geram o mesmo `_job_id` (sha256 do watermark idêntico) → Arq coalesce para 1 só job enfileirado. Severidade LOW + mitigação existente = aceitável. Fix "real" (Redis + advisory lock) teria custo-benefício desfavorável dado que o impacto (duplicatas de jobs) é já controlado.
