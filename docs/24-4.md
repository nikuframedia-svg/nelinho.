## Parte III — Real-time: SSE + WebSocket

### III.1 Porquê agora

O Blueprint §7.1 diz "*WebSocket primary, SSE fallback*". Hoje **zero** real-time no código. O que UX ganha com real-time:

| Caso de uso | Ganho observável |
|---|---|
| Alertas (molde, stock, gargalo) | De 0-30s latência para <1s |
| Timeline de Aprovação | "Aparece" em vez de refresh manual |
| Dashboard Laminagem | Utilização viva vs 30-second polling |
| Copilot streaming | Tokens a aparecer vs "loading…" |
| Trust Index changes | Gate visual muda quando dado chega |

### III.2 Decisão: SSE primeiro, WebSocket cirúrgico depois

**SSE (Server-Sent Events)** cobre 80% dos casos com 20% da complexidade:
- Uni-direccional (servidor → cliente)
- FastAPI via `sse-starlette` (~15 linhas de setup)
- Frontend `EventSource` nativo, reconnect automático
- HTTPS standard, passa por Caddy sem config extra
- Zero sticky session needed
- **Ideal para 1 servidor on-prem**

**WebSocket** só onde precisa de bi-direccional:
- Copilot streaming (cliente envia prompt, servidor stream tokens)
- Eventualmente: chat multi-user (fora de scope)

### III.3 Arquitectura concreta

```
Business logic (já emite)
    → Kafka topic (já existe)
    → RealtimeBridge (NOVO, Python asyncio consumer)
    → SSE stream endpoint (NOVO, /v1/realtime/events)
    → Browser EventSource (NOVO, React hook)
```

**Reutiliza infra existente:**
- Kafka topics de eventos — já emitidos (DECISION_EXECUTED, MOLD_MAINT_DUE, etc.)
- Trust Index v2 — pode virar eventos `TRUST_INDEX_UPDATED`
- Commit create — já publica `SCHEDULE_COMMIT_CREATED`

**Novo código:**
- `src/shared/realtime/bridge.py` — consumer Kafka → SSE queues
- `src/shared/realtime/api.py` — endpoint `/v1/realtime/events` (filtra por tenant + tópicos subscritos)
- `frontend/src/hooks/useRealtimeEvents.ts` — hook que consome SSE
- Topic filter per channel (alertas / timeline / dashboard)

## Parte VII — Decisões estruturais que condicionam tudo

1. **Real-time é SSE, não WebSocket full** — excepto Copilot streaming. Mais simples, on-prem friendly, zero sticky sessions.
2. **Kafka fica como event bus** — foi instalado e o código já emite. O outbox pattern em Postgres fica para Sprint K+ se precisarmos de air-gap mais apertado.
3. **Camada 2 antes de 3/4** — dados sintéticos destravam Camada 2 já; 3/4 precisam meses de dados reais.
4. **LLM Causal antes de 3 Umwelts** — tabelas vazias (3 dashboards) são pior do que 1 dashboard rico (actual). O investimento em causal paga-se mais depressa.
5. **Nelo ligada antes de Fase 6 (Sprint J)** — produção sem dados reais é teatro.
6. **Frontend `/admin/learned-rules` é P0** — sem UI, Camada 1 nunca sai do DETECTED e o moat nunca arranca em produção.
